TUIOS reads `~/.config/tuios/config.toml`. If `XDG_CONFIG_HOME` is set, the file is `$XDG_CONFIG_HOME/tuios/config.toml`. On the first run, TUIOS writes a `config.toml` with comments and no settings, except `[startup]`.

```bash
tuios config path     # print the path
tuios config edit     # open it in $EDITOR
tuios config reset    # overwrite it with the defaults, after asking
```

Write only what you want to change. Missing keys and missing tables take their defaults.

`config.toml` can include other files, and TUIOS also reads the `*.toml` files in `~/.config/tuios/config.d/`. `config.toml` wins over all of them. See [Split the Config](/docs/config-files).

```toml
[appearance]
theme = "nord"

[keybindings.window_management]
new_window = ["ctrl+t"]
```

Two things live outside the file: custom themes in `~/.config/tuios/themes/` and custom glyph sets in `~/.config/tuios/glyphs/`.

<Callout type="info" title="The binary is the source of truth">
`tuios list-options` prints every settable option with its type, default and accepted values. It reads the same registry the validator and the settings page use, so it always matches the build you run.
</Callout>

## Applying changes

TUIOS watches the file. A save is applied about 200 ms later, with no restart. The command palette also has a **Reload Config** entry.

A file with an error is not applied. The running settings stay, and the error is shown on screen.

Most of the file applies live. These parts do not:

| Change | When it applies |
|--------|-----------------|
| `[hooks]` | The daemon reads it at start. Run `tuios kill-server` after editing a hook the daemon runs |
| `[daemon]` | The daemon reads it at start. Run `tuios kill-server` after editing it. `tuios set-config daemon.log_level` also changes the log level of a running daemon |
| `[startup]` | The next new session |
| `scrollback_lines` | Panes opened afterwards |
| Custom theme files | See [Custom themes](#custom-themes) |

The daemon also follows the file for `[hosts]`, `[agents]`, `[notify]` and `preferred_shell`. Removing a host closes its link at once. A change that gives panes or other machines more waits for `tuios config apply`. This covers a new host, a wider `[agents.permissions]` and a wider link policy. See [Changes that wait](/docs/agents#changes-that-wait).

### Changing a setting at runtime

```bash
tuios list-options                       # every path, with default and accepted values
tuios list-options --section sidebar     # one group
tuios list-options --search "pane bg"    # fuzzy search, best match first
tuios get-config appearance.border_style
tuios set-config appearance.border_style thick
tuios config browse                      # search the options and set one, in an explorer
```

`tuios config browse` shows each option with its type, default, current value and source. Press <kbd>/</kbd> to search. Press <kbd>Enter</kbd> on an option to set it the same way as `set-config`. <kbd>q</kbd> or <kbd>Esc</kbd> leaves it. It needs a running daemon. See [Explorers](/docs/cli-reference#explorers).

`set-config` changes a running session. With a client attached, the client applies the value and writes it to the config. With no client attached, the daemon keeps the value for this session and does not write the file. A path the registry does not know is refused. An `[appearance]` option also answers to its bare name, so `border_style` and `appearance.border_style` are the same path. `set-config` cannot reach `[keybindings]`, `[hooks]`, `[hosts]`, `[tailscale]`, `[agents]` or the `[dock]` lists, because those are maps and lists rather than single values. For `[agents]` this is also a safeguard: a program in a pane cannot loosen it through TUIOS. `dock.clock.format` is the one `[dock]` key it can set.

### The in-app settings page

The settings page edits every option in the registry, in the same groups `list-options` prints. Open it with:

- <kbd>,</kbd> in window mode (`open_settings`)
- <kbd>Ctrl</kbd>+<kbd>B</kbd> <kbd>,</kbd> (`prefix_settings`)
- **Settings** in the <kbd>Ctrl</kbd>+<kbd>P</kbd> command palette

Most rows apply as you change them. Colour options open a colour picker. Two rows open editors of their own: the rail's [sections](#sections) and the dock's [components](#the-dock-table).

The page reopens on the tab, row and search you left it on. <kbd>1</kbd> to <kbd>9</kbd> go to a tab. A row whose value in force differs from its default has a dot after its name. That includes the rows the page draws by hand, such as the theme, glyph set, shared borders, pane gap, the master and column ratios, the rail's sections, max FPS, show keys, spotlight and the screen saver effect. For the pane geometry rows the value compared is the session's, not the config's. <kbd>Backspace</kbd> (or <kbd>Delete</kbd>) resets a changed row to its default, and its description says what the default is. The hand-drawn rows have no reset: <kbd>Backspace</kbd> on one says so, and you change it back with its own control. <kbd>Ctrl</kbd>+<kbd>Z</kbd> undoes the last change made on the page.

<kbd>/</kbd>, or any letter the page does not use, searches every tab. It ranks each row by its name, its config key, its value and its description, and each result names its tab. In the results, <kbd>←</kbd>, <kbd>→</kbd> and <kbd>Enter</kbd> change the row where it is, <kbd>Tab</kbd> goes to the row on its own tab, and <kbd>Esc</kbd> clears the search. The command palette reaches the same rows by name (`settings: pane background`), and `tuios list-options --search` runs the same search from a shell.

<Callout type="info" title="A save changes only the key">
The settings page writes only the key that you changed. Your comments, blank lines and key order stay. When the config has more than one file, the change goes to the file that sets the key. See [How TUIOS saves a change](/docs/config-files#how-tuios-saves-a-change).
</Callout>

#### border_style

Values: `rounded` (default), `normal`, `thick`, `double`, `block`, `outer-half-block`, `inner-half-block`, `ascii`, `hidden`, `glyphs`.

`glyphs` uses the border of the active [glyph set](#glyph-sets). `hidden` also hides the window buttons and the scrollbar, because both are drawn on the border.

#### max_fps

`max_fps` is the highest frame rate TUIOS draws at. Your terminal and your monitor can show fewer frames. A value above what they can show does not make TUIOS smoother.

```toml
[appearance]
max_fps = 144       # a number from 10 to 240
# max_fps = "auto"  # the refresh rate of your display
# max_fps = 0       # 60, the default
```

| Value | Frame rate |
|-------|------------|
| `0` | 60. This is the default |
| `10` to `240` | That number. A value outside the range moves to the nearest end |
| `"auto"` | The refresh rate of your display, from 10 to 240. If TUIOS cannot find the rate, it uses 60 |

The settings page offers Auto, 30, 60, 90, 120, 144, 165 and 240. With Auto selected, the row shows the rate in use, for example `Auto (144)`. A change applies at once, with no restart.

- **What you see.** TUIOS sends a frame to your terminal, and the terminal draws it on its own schedule. kitty and Ghostty draw at most once for each refresh of the monitor, so a 60 Hz monitor shows at most 60 frames a second. Over SSH, the network and the remote terminal set the limit too.
- **What it costs.** TUIOS draws only when something on the screen changes. The terminal library under it still wakes at `max_fps` while TUIOS is idle. An idle TUIOS at 240 wakes about three times as often as at 60.
- **How auto finds the rate.** TUIOS looks once in the background when it starts, and again when the config file reloads. Until the answer arrives, it draws at 60. On Wayland it asks `hyprctl` on Hyprland, `niri` on niri and `wlr-randr` on other wlroots compositors. On X11, or on another compositor, it asks `xrandr --current`. On macOS it asks `system_profiler SPDisplaysDataType`. On Windows it does not look, and uses 60.
- **Several displays.** A terminal window cannot tell which display it is on, so auto uses the highest rate among them.
- **Remote clients.** Over SSH, in `tuios-web` and in the SSH server, auto uses 60, because the displays on the machine are not the ones you see.

### Backgrounds

A cell with no background of its own is transparent, so your terminal's own background shows through. That is the default everywhere: pane content left on the default background, the space between panes, the borders, the dock and the rail. These options paint those cells instead, one surface at a time or all at once.

| Key | Surface | Default |
|-----|---------|---------|
| `background` <Since config="appearance.background" /> | Every surface below that is not set on its own | `"off"` |
| `pane_background` <Since config="appearance.pane_background" /> | Pane content, the thin scrollbar over it, and the scrollback browser | `""` (follows `background`) |
| `desktop_background` <Since config="appearance.desktop_background" /> | Behind and between panes: gaps, the space around floating panes, an empty workspace and its welcome screen | `""` |
| `window_chrome_background` <Since config="appearance.window_chrome_background" /> | Pane borders and title bars, and the lines between shared borders | `""` |
| `dock_background` <Since config="appearance.dock_background" /> | The dock | `""` |
| `sidebar.background` <Since config="appearance.sidebar.background" /> | The rail, under `[appearance.sidebar]` | `""` |

Each takes `off`, `theme` or a `#RRGGBB` colour:

- `off` paints nothing, so your terminal's background shows through.
- `theme` paints the active theme's background, with the theme's foreground on default-coloured text. With no theme set, it behaves as `off`.
- `#RRGGBB` paints that colour. With a theme set, default-coloured text takes the theme's foreground, lightened or darkened until it reads on the colour.

A surface's own option wins whenever it holds a value, `off` included. Left empty, it follows `background`:

```toml
[appearance]
background = "theme"          # every surface on the theme's background
dock_background = "#11111b"   # the dock a shade darker
pane_background = "off"       # panes keep the terminal's own background

[appearance.sidebar]
background = "#181825"
```

Only cells with no background of their own are painted. A background a program chose, the selection and search marks, and the colours the chrome sets itself always win. A value that is not a keyword or a `#RRGGBB` colour reads as `off` for that surface, with a validation warning.

While the pane background paints a colour, a program that asks the terminal for its colours (OSC 10 and 11) is told the colours it is drawn on, so it can pick a light or dark palette. All six options apply live, reach every attached client, and are on the **Backgrounds** tab of the settings page, where <kbd>x</kbd> clears a surface back to following `background`.

#### window_title_format

A template for every title. It expands three placeholders:

- `{title}`: the custom name, or the title the program set
- `{index}`: the window's 1-based position in its workspace
- `{cwd}`: the window's working directory

```toml
[appearance]
window_title_format = "{index}: {title} ({cwd})"
```

Any other `{...}` produces a validation warning and is drawn as written.

#### Links

<kbd>Ctrl</kbd>+click on a link opens it. <kbd>Ctrl</kbd>+drag still moves the pane: a link opens only when the pointer does not move. Only `http`, `https`, `mailto`, `ftp` and `ftps` links go to the opener. TUIOS copies other links. Under `ssh`, on a remote client, or on a machine with no desktop, TUIOS copies the URL, and your terminal can still open the link from the OSC 8 that TUIOS writes. If the opener fails, the dock says so and TUIOS copies the URL. See [Links](/docs/links) for the opener, the safety rules and a table of terminals.

### Workspace tab style <Since config="dock.tabs" /> [#workspace-tab-style]

By default the workspace strip draws rounded pills. `[dock.tabs]` can draw flat tabs, the way a tmux status line draws its window list:

```toml
[appearance]
dock_workspace_tab_format = "{name}{zoom} {icon}"

[dock.tabs]
style         = "flat"        # pill (default) or flat
separator     = " • "         # drawn between flat tabs
separator_fg  = "#4c3743"
active_fg     = "#272e33"
active_bg     = "#a7c080"
active_bold   = true
inactive_fg   = "#4f5b58"
number_glyphs = ["I", "II", "III"]  # {icon}: the first entry is workspace 1
zoom_marker   = " [ ]"        # {zoom} on the current workspace while a pane is zoomed
show_add      = false         # keep the "+" tab in the flat style
```

| Key | What it does |
|-----|--------------|
| `style` | `pill` (the default) or `flat` |
| `separator`, `separator_fg` | The text between flat tabs, and its colour |
| `active_fg`, `active_bg`, `active_bold` | The current tab |
| `inactive_fg`, `inactive_bg`, `inactive_bold` | The other tabs |
| `number_glyphs` | The text of `{icon}` for each workspace. A workspace past the end of the list shows its number |
| `zoom_marker` | The text of `{zoom}` on the current workspace while a pane is zoomed |
| `show_add` | Keep the `+` tab in the flat style |

Colours are `#rrggbb`, and they are overrides. With no colour set, a flat strip draws the current tab in bold on the theme's accent, and the other tabs in dim text. tuios ignores a colour that is not `#rrggbb` and shows a warning. The flat style shows even one workspace, and drops the `+` tab unless `show_add` is on. With no `[dock.tabs]` table, the strip does not change.

To reorder the dock or add your own cells, see [The dock table](#the-dock-table).

### Clipboard writes from a pane

A program in a pane sets the clipboard with OSC 52. An editor uses OSC 52 to yank over ssh. Any output can also carry OSC 52, for example a file that a program prints. `appearance.selection.osc52_write` controls what happens.

| Value | What happens |
|---|---|
| `off` | The host clipboard does not change. |
| `ask` | The dock shows a message. Click the message to copy the text. |
| `focused` | The focused pane copies. A write from another pane shows a message in the dock. This is the default. |
| `on` | Every pane copies. This is the behaviour of v0.8.0. |

```toml
[appearance.selection]
osc52_write = "focused"
```

- When the focused pane copies text with a line break or a control character, the dock shows one line for that pane. A one-line copy shows nothing.
- Each pane keeps one clipboard ask. A click copies only the text that the dock shows. If the text changes first, click the new message.
- A pane that runs without the daemon keeps its own copy of the text. The program reads it back with an OSC 52 query. A pane under the daemon keeps no copy, so an OSC 52 query there always gets an empty answer.
- TUIOS drops a clipboard reply that answers no read request of TUIOS.

Pastes, notifications, OSC 66 text and link addresses lose their control characters. A paste into a pane keeps its tabs and line breaks. Text that holds `ESC[201~` cannot end a bracketed paste early.

#### sections

One string sets which sections the rail draws, their order from the top, and the share of the rail each may take.

```toml
[appearance.sidebar]
sections = "sessions:25,terminals,files:25,agents:34"
```

- Separate sections with commas. Add `:N` for a share in percent.
- The section names are `sessions`, `terminals`, `files`, `agents`, `git` and `custom`. Leave a name out to hide that section. See [The custom section](#the-custom-section).
- A share is a ceiling, not a reservation. A section only takes the lines its rows fill. A section with no share takes what the others leave.
- `spacer` draws nothing and takes lines. It is the only name you can repeat. A spacer with a share keeps that share. A spacer with no share takes the lines nothing else wants, which pushes what follows to the bottom.

```toml
[appearance.sidebar]
# Sessions at the top, files at the bottom
sections = "sessions:30,terminals,spacer,files:40"
```

An unknown name, a bad percent or a repeated section is dropped and reported as a config warning.

The settings page has an editor for this: the **Sections** row under Sidebar. Arrows select, <kbd>Shift</kbd>+arrows move, <kbd>Enter</kbd> adds or removes a section, <kbd>←</kbd>/<kbd>→</kbd> change the share, <kbd>r</kbd> restores the default and <kbd>u</kbd> undoes your edits.

#### The files section

The files section lists the focused pane's directory. It is read again when the shell changes directory, when the focus moves and when a client attaches. It is also read again when a file in the listed folder is added, removed or renamed, by the pane or by another program. tuios asks the system to report these changes (inotify on Linux, kqueue on macOS and the BSDs, ReadDirectoryChangesW on Windows). Nothing polls, and a change to the contents of a file does not cause a read. For a pane on another machine, the list changes only when the shell changes directory.

`folder_click` decides what a click on a folder does: `navigate` opens it in the listing, `cd` sends the focused pane there, `both` does both. A `cd` is only typed into a pane that is at a shell prompt.

The file keys are in `[keybindings.sidebar_files]` and work while the rail has the keyboard and the cursor is on a file row. See [Keybindings](/docs/keybindings#session-rail). Each action opens a centred dialog. The delete dialog opens on Cancel, so <kbd>Enter</kbd> on an untouched dialog deletes nothing.

Delete uses the freedesktop.org trash in your home directory, so your desktop's trash shows the file and can restore it. <kbd>D</kbd> deletes permanently. Set `file_delete = "permanent"` to make <kbd>d</kbd> permanent too. The per-volume trash is not implemented.

<kbd>Y</kbd> copies the absolute path of the selected file or folder. A folder's context menu has a **Copy path** row that does the same.

On Windows, a shell under MSYS2 or Cygwin reports its folder as `/c/work`. TUIOS reads that as `C:\work`, by the rules of `cygpath`, so the files section lists the right folder.

#### The file editor

<kbd>Shift</kbd>+<kbd>Enter</kbd> on a text file opens it in a terminal editor. `editor` sets the command. The settings page shows it as **File editor** under Sidebar.

```toml
[appearance.sidebar]
editor = "micro"
```

- Other terminal editors and arguments work too, such as `nano` or `vim -f`.
- Quote a path or an argument that contains spaces. TUIOS splits the command into arguments and runs no shell.
- TUIOS adds the full path of the file at the end.
- When `editor` is empty, TUIOS uses `$EDITOR`, then `$VISUAL`, then `vi`.
- File links and hints open files with the same command.
- TUIOS reads the first 512 bytes of a file to check that it is text. It refuses binary files and special files.

#### The custom section

The `custom` section shows the output of a command you write. Place `custom` in `sections` and describe it in `[appearance.sidebar.custom]`:

```toml
[appearance.sidebar]
sections = "sessions:25,terminals,custom:35,agents:30"

[appearance.sidebar.custom]
title   = "Brief"
command = "agent-brief render"
refresh = "event:window-focused,agent-state"
```

| Key | What it does |
|-----|--------------|
| `title` <Since config="appearance.sidebar.custom.title" /> | The section's heading. Defaults to `Custom` |
| `command` <Since config="appearance.sidebar.custom.command" /> | Run with `sh -c`. Every line of stdout is a row |
| `refresh` <Since config="appearance.sidebar.custom.refresh" /> | `once` (the default), a duration such as `"30s"` (one second at least), or `event:TYPE[,TYPE...]` with the dock's event types. `push` is refused |

The command follows the rules of a [dock component](#custom-components). It runs in the client, under a three second timeout, with bounded output. SGR colour stays, and every other control sequence is removed. A command that fails, times out or prints nothing leaves the title over an empty section. Five failures in a row stop it until the config reloads or you run `tuios refresh-dock rail/custom`. `tuios list-dock-components` lists it as `rail/custom`. Rows are cut to the rail's width and to the section's lines, with `… +N` for the rows below.

Each run gets the client's environment and these variables: `TUIOS_SESSION`, `TUIOS_SOCKET`, `TUIOS_RAIL_SECTION` (`custom`), `TUIOS_RAIL_WIDTH`, `TUIOS_RAIL_HEIGHT`, `TUIOS_ACTIVE_PANE_ID` and `TUIOS_ACTIVE_PANE_CWD`. An event that arrives during a run causes one more run after it, so a quick focus change never leaves the old pane's rows on screen. The command does not run while the rail is hidden or folded.

`sections` works with `tuios set-config`. `[appearance.sidebar.custom]` is read from the file only, so a program in a pane cannot change the command.

#### Two edges <Since config="appearance.sidebar.left.enabled" /> [#two-edges]

The rail can show on both edges of the screen at the same time. `[appearance.sidebar]` still configures the original rail. Add `[appearance.sidebar.left]` or `[appearance.sidebar.right]` to configure one edge:

```toml
[appearance.sidebar]
position = "right"
sections = "sessions,terminals,custom"

[appearance.sidebar.custom]
command = "right-summary"

[appearance.sidebar.left]
enabled = true
width = 28
sections = "sessions,files,custom"

[appearance.sidebar.left.custom]
command = "left-summary"
```

| Key | What it does |
|-----|--------------|
| `enabled` | Show a rail on this edge. The edge opposite `position` stays hidden until you set `enabled = true` |
| `width` | The preferred width of the rail on this edge, in columns |
| `sections` | The section layout of this edge. See [sections](#sections) |
| `custom` | A table with the `command` of this edge's custom section |
| `session` <Since config="appearance.sidebar.left.session" /> | The name of a daemon session to show in this rail. Its panes stack top to bottom in place of the sections. Empty shows the sections. See [A daemon session in a rail](/docs/session-rail#a-daemon-session-in-a-rail) |
| `session_workspace` <Since config="appearance.sidebar.left.session_workspace" /> | Show the session rail only on this workspace, `1` to `9`. `0`, the default, shows it on every workspace |

- On the edge of `position`, the edge table overrides only the keys it sets. The other keys come from `[appearance.sidebar]`.
- On the other edge, a key you do not set takes its default. An unset `sections` takes the default section order.
- With `position = "hidden"`, an edge table with `enabled = true` still draws. When both edges are on, the left one is the original rail.
- Each rail has its own scroll, keyboard focus and custom command. Both read the same sessions, files and git state.
- On a narrow screen, the second rail closes before the original rail.

Each edge table also takes the five `subagent_*` keys. A key that the edge table does not set uses the value from `[appearance.sidebar]`. See [Subagent rows](/docs/session-rail#subagent-rows).

The edge tables are read from the file only. `tuios set-config` cannot change them, because a custom command runs outside the panes. <kbd>Ctrl</kbd>+<kbd>B</kbd> <kbd>H</kbd> shows or hides the second rail. See [Session Rail](/docs/session-rail#both-edges).

#### Agent rows

`[appearance.sidebar.agent_row]` chooses which tokens an agent row shows and styles each one, with optional rules that match on the token's value:

```toml
[appearance.sidebar.agent_row]
tokens = ["session", "need", "harness", "name", "elapsed", "context", "subagents", "pr", "meta", "now", "message"]

[[appearance.sidebar.agent_row.elapsed.rule]]
gt = 30          # minutes in the current state
fg = "warning"
```

The `tokens` above are the shipped list. The other tokens are `state`, `host` and `prompt`. A `tokens` list you wrote keeps its own order and gets no new tokens, so add `subagents` or `pr` to it to see them. `need` says what a row wants from you, such as `approval` or `question`. `context` shows `ctx 84%` once the agent's context is 80% full. `now` is what a working agent is doing, such as `Bash: go test ./...`. `subagents` shows how many subagents a Claude Code agent has at work, such as `3 subagents`, on any row while any run. When the subagents have rows of their own, it reads `3 of 4 run`. `pr` shows the pull request of the session's worktree branch and its checks, such as `PR #12 open pass`. `meta` draws the other keys the pane reported with `tuios set-agent-meta`, and `$` followed by a key, such as `$model` or `$cost`, places one key. See [Session Rail](/docs/session-rail#agent-rows).

Each rule has one test: `equals`, `contains`, `starts_with`, `gt` or `lt`. The first matching rule wins. A mistake in this table is a warning, not an error.

## Splits that follow ssh

The actions `split_ssh_horizontal`, `split_ssh_vertical` and `new_window_ssh` open a pane on the machine that the focused pane is connected to with ssh. See [Keybindings](/docs/keybindings#split-into-the-same-ssh).

`appearance.new_window_follow_ssh` makes the ordinary actions do the same: `split_horizontal`, `split_vertical` and `new_window`. When the focused pane does not run ssh, these actions open an ordinary pane. The default is `false`.

```toml
[appearance]
new_window_follow_ssh = true
```

tuios finds ssh in the foreground of the pane. ssh can run from a shell, or from `sshpass`, `autossh` or `mosh`. tuios reads only the processes that you own in the pane. It runs the `ssh` or `mosh` that it finds on its own `PATH`, with no shell on this machine. It never runs the program that the pane runs.

The new ssh gets the same environment as an ordinary new pane. If the ssh that tuios follows has an `SSH_AUTH_SOCK` that names your own agent socket, the new ssh gets that value too. An agent that your shell started in the pane then works in the split. The socket must not be a link, and its folder must be yours and closed to other users.

The new ssh line keeps only what it needs to reach the same host as the same user. It always gets `-o ControlMaster=no`. Your `~/.ssh/config` applies to it as usual, so a setting that you put there still works in the split.

### Lines that are not followed

tuios follows an ssh line only when each `-o` option is on one of two lists. The new pane keeps these options:

`AddressFamily`, `BatchMode`, `CertificateFile`, `CheckHostIP`, `Ciphers`, `Compression`, `ConnectionAttempts`, `ConnectTimeout`, `EscapeChar`, `HostKeyAlgorithms`, `HostName`, `IdentitiesOnly`, `IdentityFile`, `KbdInteractiveAuthentication`, `KexAlgorithms`, `LogLevel`, `MACs`, `PasswordAuthentication`, `Port`, `PreferredAuthentications`, `ProxyJump`, `PubkeyAcceptedAlgorithms`, `PubkeyAuthentication`, `ServerAliveCountMax`, `ServerAliveInterval`, `StrictHostKeyChecking`, `TCPKeepAlive` and `User`.

The new pane does not get these options, and tuios still follows the line:

- Forwards and sessions: `LocalForward`, `RemoteForward`, `DynamicForward`, `GatewayPorts`, `ExitOnForwardFailure`, `ClearAllForwardings`, `Tunnel`, `TunnelDevice`, `RemoteCommand`, `SessionType`, `StdinNull`, `ForkAfterAuthentication` and `RequestTTY`.
- Files, sockets, environment and forwarding: `ControlMaster`, `ControlPersist`, `ControlPath`, `UserKnownHostsFile`, `GlobalKnownHostsFile`, `HostKeyAlias`, `IdentityAgent`, `SendEnv`, `SetEnv`, `ForwardAgent`, `ForwardX11` and `ForwardX11Trusted`.
- The flags `-A`, `-X`, `-Y`, `-S`, `-L`, `-R`, `-D`, `-W`, `-w`, `-N`, `-f`, `-n`, `-T`, `-t`, `-M` and `-s`.

These ssh lines get an ordinary pane:

- An `-o` option that is not on the two lists above. `ProxyCommand`, `LocalCommand`, `XAuthLocation` and `Match` are examples.
- An option or a value with a control character, such as a line break.
- `-E`, `-F`, `-I`, `-G`, `-V`, `-Q` and `-O`, and an option that tuios does not know.
- A `-J` or `ProxyJump` hop that is not `[user@]host[:port]` or the `ssh://` form, made of letters, digits and `._:@[]-`, or a hop that starts with `-`.
- A mosh destination that starts with `-`.
- mosh with `--ssh`, `--client` or `--server`.
- ssh that another program starts, such as `scp`, `rsync`, `git` or `sftp`.

Put a `ProxyCommand` or a `ProxyJump` in `~/.ssh/config` to use it with a split. A split with `-J` on the command line is followed.

### Start in the remote folder

The new pane starts in the remote folder when the remote shell reports its folder with OSC 7. The host name in the report must be the same as the host in the ssh line, or as the `HostName` that `ssh -G` gives for that line. `reachy-mini` matches `pollen@reachy-mini`. When `~/.ssh/config` makes `prod` an alias for `box.example.com`, a report from `box.example.com` or from `box` matches `ssh prod`. A report from `box.other.com` does not. When there is no match, the new pane starts in the remote home folder.

fish sends the report by default. For bash, add this line to `~/.bashrc` on the remote machine:

```bash
PROMPT_COMMAND='printf "\033]7;file://%s%s\033\\" "$HOSTNAME" "$PWD"'${PROMPT_COMMAND:+;$PROMPT_COMMAND}
```

For zsh, add these lines to `~/.zshrc` on the remote machine:

```zsh
autoload -Uz add-zsh-hook
_tuios_osc7() { printf '\e]7;file://%s%s\e\\' "$HOST" "$PWD" }
add-zsh-hook precmd _tuios_osc7
```

To go to the folder, tuios adds `-t`, `-o RemoteCommand=none` and the command `exec sh -c 'cd "FOLDER" ...'` to ssh. This works with every login shell that can start `sh`. If the folder is gone, the new pane starts in the home folder. A folder name with a quote, `$`, a backslash or `!` is not used. A Windows folder, such as `C:/Users/x` or a network share `//server/share`, is not used either, because a Windows ssh server has no `sh`. The new pane then starts in the home folder.

## Glyph sets

A theme sets the chrome's colours. A glyph set sets its shapes: border corners, window buttons, rules, separators and rail marks.

```toml
[appearance]
glyphs = "heavy"
```

```bash
tuios list-glyphs            # every set, and every role name
tuios list-glyphs heavy      # what this set draws, role by role
tuios set-config appearance.glyphs heavy
```

| Id | What it is |
|----|------------|
| `default` | Rounded frame, Nerd Font powerline caps, `✕` and `□` buttons |
| `unicode` | Box drawing and geometric shapes, with no Nerd Font glyphs |
| `heavy` | One stroke weight heavier throughout |
| `ascii` | 7-bit ASCII only |

A set's border is used only when `border_style = "glyphs"`. This keeps a set from silently overriding a border style you chose. A set that defines only some border runes gets the rounded border for the rest.

### Writing a set

Save `<id>.json` in the glyphs directory. `tuios list-glyphs` prints its path.

```json
{
  "display_name": "Mine",
  "inherits": "heavy",
  "bullet": "◦",
  "focus": "▐",
  "border": {
    "top_left": "╔",
    "top_right": "╗",
    "bottom_left": "╚",
    "bottom_right": "╝"
  }
}
```

Every field is optional. The id defaults to the file name. A role you do not set comes from the inherited set, and finally from `default`. Inheritance goes up to eight levels deep.

The roles:

- **Window buttons:** `close`, `maximize`, `minimize`, `dot`, `pill_left`, `pill_right`
- **Rules and separators:** `rule`, `separator`, `arrow_left`, `arrow_right`, `dash_rule`
- **Rail marks:** `focus`, `attention`, `bullet`, `add`, `collapse`, `expand`, `fold_open`, `fold_shut`, `tree_branch`, `tree_last`
- **Files section:** `folder`, `parent`, `file`
- **Scrollbar:** `scrollbar_thumb`, `scrollbar_track`
- **Text:** `ellipsis`, `sigil`
- **Border:** `border.top`, `border.bottom`, `border.left`, `border.right`, the four corners, and the junctions `middle`, `middle_top`, `middle_bottom`, `middle_left`, `middle_right`

Most roles must be exactly one cell wide, because the window buttons' click areas are fixed offsets. A glyph of the wrong width falls back to the default. `separator`, `ellipsis`, `collapse` and `expand` may be any width. To see what was dropped:

```bash
tuios list-glyphs mine --json | jq -r '.problems[]?'
```

The directory is read again on every lookup, so a new file can be selected at once. A file that does not parse is skipped and listed under `problems`.

`--ascii-only` replaces non-ASCII glyphs role by role, so a set keeps every role it already spelled in ASCII. A glyph set never changes colours, and it does not change the dock's icons.

The settings page has a **Glyph set** row under **Theme**. Its picker applies each set as you move through the list.

## Themes

342 themes ship with TUIOS.

```bash
tuios --list-themes                   # every theme id
tuios --preview-theme dracula         # the 16 ANSI colours
tuios list-themes --filter gruvbox    # from a running daemon, with --json
tuios list-themes catppuccin_mocha    # colours and their contrast
```

```toml
[appearance]
theme = "dracula"
```

With no theme, TUIOS uses your terminal's own colours. A theme only changes ANSI colours 0 to 15. 256-colour and truecolor output is drawn as the program wrote it.

To pick one in the app, press <kbd>Enter</kbd> on the **Theme** row of the settings page, or choose **Theme Picker** in the command palette. The picker previews as you move and <kbd>Esc</kbd> restores the theme you had. It has no key binding.

### Custom themes

Save one theme per JSON file in `~/.config/tuios/themes/`. Subdirectories are ignored.

```json
{
  "id": "my-theme",
  "display_name": "My Theme",
  "fg": "#e0def4",
  "bg": "#191724",
  "black": "#26233a",
  "red": "#eb6f92",
  "green": "#31748f",
  "yellow": "#f6c177",
  "blue": "#9ccfd8",
  "purple": "#c4a7e7",
  "cyan": "#ebbcba",
  "white": "#e0def4"
}
```

- `id` defaults to the file name, lowercased. `display_name` defaults to `id`.
- The colour names are `black`, `red`, `green`, `yellow`, `blue`, `purple`, `cyan`, `white`, each with a `bright_` variant, plus `fg`, `bg` and `cursor`. Note `purple`, not `magenta`.
- A missing colour gets the xterm default. A missing `bright_*` colour copies its normal colour, so set them if you want bright text to look different.
- An optional `chrome` object sets the UI colours directly (`accent`, `accent_bright`, `success`, `warning`, `error`, `info`, `surface`) without changing the pane palette.
- A file that does not parse is skipped and logged.

`tuios import-theme <file>` converts a kitty, Ghostty, Alacritty or WezTerm scheme into a file here.

Selecting an id that is not registered yet, with `set-config` or the settings page, reads the directory again first. So does `tuios list-themes`. The picker builds its list when it opens.

## Notifications

`[notifications]` sets how long messages stay on screen. `0` uses the built-in default.

| Key | Default | What it does |
|-----|---------|--------------|
| `duration` <Since config="notifications.duration" /> | `0` | Seconds an info or success message stays up |
| `warning_duration` <Since config="notifications.warning_duration" /> | `0` | Seconds a warning stays up |
| `error_duration` <Since config="notifications.error_duration" /> | `0` | Seconds an error stays up when `error_sticky` is off |
| `error_sticky` <Since config="notifications.error_sticky" /> | `true` | Errors stay until you press <kbd>Esc</kbd> |

### Agent alerts

`[notifications.agent]` controls what happens when an agent in a pane changes state.

| Key | Default | What it does |
|-----|---------|--------------|
| `enabled` <Since config="notifications.agent.enabled" /> | `true` | Turn every agent alert on or off |
| `notify` <Since config="notifications.agent.notify" /> | `true` | Send a desktop notification through the terminal (OSC 9, so it works over SSH) |
| `dock` <Since config="notifications.agent.dock" /> | `true` | Show the alert in the dock. Click it to go to the pane |
| `sound` <Since config="notifications.agent.sound" /> | `false` | Make the alert audible |
| `sound_mode` <Since config="notifications.agent.sound_mode" /> | `"audio"` | `audio` plays a cue, `bell` sends BEL, `both` does both |
| `sound_cooldown_seconds` <Since config="notifications.agent.sound_cooldown_seconds" /> | `3` | Shortest gap between two sounds, across all panes |
| `command` <Since config="notifications.agent.command" /> | `""` | Shell command to run on an alert |
| `settle_seconds` <Since config="notifications.agent.settle_seconds" /> | `2` | Wait this long, and drop the alert if the pane leaves the state |
| `suppress_focused` <Since config="notifications.agent.suppress_focused" /> | `true` | No alert for the pane you are looking at |
| `quiet_hours` <Since config="notifications.agent.quiet_hours" /> | `""` | `HH:MM-HH:MM` in local time when nothing alerts |

`[notifications.agent.states]` turns alerts on per state: `needs_input`, `errored` and `done` default to `true`. `idle` and `working` default to `false`.

To hear an alert, set `sound = true`. `sound_mode` then decides how:

- `audio` plays a short cue through the audio player of the machine that runs TUIOS: `paplay`, `pw-play` or `aplay` on Linux, `afplay` on macOS, PowerShell on Windows. If the machine has no player, the alert is silent and TUIOS shows no message.
- `bell` sends a BEL character to your terminal. Your terminal decides what a bell does, and some terminals make no sound. In kitty, check that `enable_audio_bell` is `yes`. Other terminals have a similar bell setting.
- `both` does the two.

Over SSH or in the browser, `audio` plays on the server, not where you sit. Use `bell` there. See [Agents](/docs/agents#hear-an-alert).

`[notifications.agent.sounds]` replaces the two built-in cues with your own files: `needs_input` (also used for `errored`) and `done` (also used for `idle`). A path that does not exist falls back to the built-in cue.

The `after-agent-state` [hook](/docs/hooks) follows the same rules, including the settle wait.

### Mail alerts

`[notifications.mail]` controls the alerts for mail to you and for session notices. A key that you leave out uses the same key from `[notifications.agent]`.

| Key | Default | What it does |
|-----|---------|--------------|
| `enabled` <Since config="notifications.mail.enabled" /> | follows `notifications.agent.enabled` | Turn mail alerts on or off |
| `notify` <Since config="notifications.mail.notify" /> | follows `notifications.agent.notify` | Send a desktop notification |
| `dock` <Since config="notifications.mail.dock" /> | follows `notifications.agent.dock` | Show the alert in the dock. Click it to open the thread |
| `sound` <Since config="notifications.mail.sound" /> | follows `notifications.agent.sound` | Make the alert audible |
| `between_agents` <Since config="notifications.mail.between_agents" /> | `false` | Also alert on a message from one agent to another |

TUIOS warns when `between_agents` is on and mail alerts are off.

The sound mode, the cooldown, the cue files and the quiet hours always come from `[notifications.agent]`. `tuios set-config notifications.mail.sound ""` clears a key, and `get-config` then prints `(follows notifications.agent.sound)`. See [Agent Messaging](/docs/agent-messaging#mail-alerts).

### Key syntax

- **Modifiers:** `ctrl+`, `alt+`, `shift+`, `super+`. Also `opt+` and `option+`, which mean `alt+`, `cmd+` and `command+`, which mean `super+`, and `control+`, which means `ctrl+`. These spellings work on every platform.
- **Special keys:** `enter`, `return`, `esc`, `escape`, `tab`, `space`, `backspace`, `delete`, `up`, `down`, `left`, `right`, `home`, `end`, `pgup`, `pageup`, `pgdown`, `pagedown`, `f1` to `f12`.
- **Any single character:** letters, digits, symbols, and accented letters.
- **Held modifiers:** `leftalt`, `rightalt`, `leftctrl`, `leftsuper` and the like, for `hold_window_mode` only. They need the Kitty keyboard protocol.

`super+` only reaches TUIOS in terminals that speak the Kitty keyboard protocol. On Linux, `opt+1` is `alt+1`. See [One config on macOS and Linux](#one-config-on-macos-and-linux).

```toml
new_window = ["n", "ctrl+t"]   # several keys for one action
close_window = []              # no key: the key goes to the pane
```

An empty list is different from a missing line. A missing action gets its default back at the next load. An empty list stays empty.

`shift+1` and `!` are the same key, and so are `shift+a` and `A`. Binding one spelling binds both. Do not bind the two spellings to different actions.

### Keyboard layout and Option characters

```toml
[keybindings]
keyboard_layout = "us"   # us, other
option_glyphs = "auto"   # auto, alt, bind, type
```

| Key | Default | What it does |
|-----|---------|--------------|
| `keyboard_layout` <Since config="keybindings.keyboard_layout" /> | `us` | `us` lets a binding on `opt+shift+7` also match `opt+&`, as on a US keyboard. Set `other` for AZERTY, QWERTZ and other layouts. A key that the terminal reports through the Kitty keyboard protocol uses that report. |
| `option_glyphs` <Since config="keybindings.option_glyphs" /> | `auto` <Since feature="option-glyphs-auto" /> | What a character that macOS Option typed does. `auto` reads the keyboard layout of the Mac when tuios starts. On a US or ABC layout it runs the Option binding for the character. On other layouts the character goes to the pane. A `keyboard_layout` that you set overrides the layout of the Mac. `alt` runs the binding only when the terminal also reports Alt. `bind` always runs it. `type` always sends the character to the pane. |

See [Shifted digits and AZERTY](/docs/keybindings#shifted-digits-and-azerty) and [One Option key for typing](/docs/keybindings#one-option-key-for-typing).

### Platform defaults

On macOS, the workspace and preselect defaults use `opt+`, and `terminal_mode` adds `opt+tab`, `opt+shift+tab` and `opt+esc`. Writing `alt+` on macOS works but gives an advisory warning. Elsewhere the defaults use `alt+`. See [Keybindings](/docs/keybindings#terminal-mode).

A change to `single_client`, `ssh_agent` or `display` in the file applies to the next attach.

### The display of the client <Since config="daemon.display" /> [#the-display-of-the-client]

A daemon that a host link starts over ssh has no `WAYLAND_DISPLAY` or `DISPLAY`. Its panes have none either, so `wl-copy`, `wl-paste`, `xclip` and image paste fail. With `display = "follow"`, the default, the new panes of such a daemon get the display of the local client that attached to the session or used it last.

```toml
[daemon]
display = "follow"
```

- A daemon that has a `WAYLAND_DISPLAY` or a `DISPLAY` of its own keeps it. The option does nothing then.
- Each session has a link to the Wayland socket of the client: `wayland-<session id>.sock`, in the folder of the daemon socket. A new pane gets `WAYLAND_DISPLAY` set to the full path of the link. The link moves to the socket of the newest client.
- A new pane also gets `DISPLAY` and `XAUTHORITY` of the client. `DISPLAY` is a name, not a path, so a pane keeps the value it started with.
- A shell that started before a desktop client attached has no display. Run `eval "$(tuios display-env 2>/dev/null)"` in that shell, or add the line to your shell rc. See [`tuios display-env`](/docs/cli-reference#display-env).
- When the client detaches, the session uses the display of the client before it. When no attached client has a display, tuios removes the link, and new panes get no display.
- tuios uses the display of `tuios attach` and `tuios new` only. The client must run on this machine, as your user, and outside every pane. tuios ignores a client that comes through a host link, a client of the tuios SSH server and a client of `tuios-web`.
- A `WAYLAND_DISPLAY` name such as `wayland-1` is looked up in the `XDG_RUNTIME_DIR` of the client, then in the one of the daemon, then in `/run/user/<uid>`. The client does not need `XDG_RUNTIME_DIR`.
- The Wayland socket must be a Unix socket that you own. `DISPLAY` must be `:N` or `:N.S`, and tuios ignores a forwarded display such as `localhost:10.0`. `XAUTHORITY` must be a file that you own.
- The option is read from the file only. `tuios set-config` cannot change it.

To change `window_size` for one session while it runs, use `tuios set-config daemon.window_size smallest -s NAME`. That value is not saved to the file. A change in the file applies when the daemon starts again.

`tuios set-config daemon.log_level messages` changes the level of a running daemon at once. `verbose` and `trace` also log pane content, window titles and paths. `tuios logs` reads the log.

## The startup table

`[startup]` decides how a new session starts. It never changes a running session.

| Key | Default | What it does |
|-----|---------|--------------|
| `daemon` <Since config="startup.daemon" /> | `true` | A bare `tuios` attaches to a daemon session instead of running standalone |
| `tiled` <Since config="startup.tiled" /> | `true` | Start with tiling on |
| `layout` <Since config="startup.layout" /> | `"bsp"` | Tiling layout: `bsp`, `master-stack` or `scrolling` |

<Callout type="info" title="Older config files keep their behaviour">
`daemon` and `tiled` default to `true` in a new install. A config file that already exists and does not mention them reads them as `false`, so an upgrade keeps the floating, standalone start it had. Add the keys to opt in.

In the same way, v0.8.0 changed eight appearance defaults: the rail is on, on the right, 24 columns wide; the dock and the window titles are on top; a zoomed pane takes 95% of the screen; a double click starts typing; and the scrollbar is a track. A config file that sets one of these keys keeps its value. The first-run file older releases wrote names most of them, so such an install keeps the old look until you remove those lines.
</Callout>

A session keeps its own layout once it is running. Attaching never rearranges a session to match your config.

## The workspaces table

When the last pane on the workspace on screen closes, TUIOS shows the workspace you came from. This happens when the pane's program stops, when you close the pane, when `tuios xpanes -ss` closes it, and with `tuios close-workspace`.

| Key | Default | What it does |
|-----|---------|--------------|
| `return_when_empty` <Since config="workspaces.return_when_empty" /> | `true` | Show the workspace you came from when the workspace on screen becomes empty. `false` keeps the empty workspace on screen |
| `new_window_when_empty` <Since config="workspaces.new_window_when_empty" /> | `false` | Open a pane when you switch to a workspace that has no panes, as the new-window key does |

TUIOS goes back in this order:

1. For a workspace that `tuios xpanes` opened, the workspace where you ran `tuios xpanes`.
2. The workspace you showed last that still has panes. After a chain of empty workspaces, TUIOS goes back past each one.
3. The workspace with the lowest number that has panes.

When no workspace has panes, TUIOS shows the splash screen. The workspace on screen is the same for every client of the session, so every client goes back. A pane that moves to another workspace does not close, so TUIOS does not go back.

```toml
[workspaces]
return_when_empty = false
```

The daemon reads the setting when it starts and when the file changes. `tuios set-config workspaces.return_when_empty false` changes it while TUIOS runs.

### A pane on an empty workspace

By default, a workspace with no panes shows the splash screen. To open a pane there when you switch to it, as tabs do in other multiplexers, turn on `new_window_when_empty`:

```toml
[workspaces]
new_window_when_empty = true
```

The new pane starts in the folder of the pane that had focus on the workspace you came from. It starts in the session's start folder (the folder that `tuios new --cwd` gave) when you came from a workspace with no pane, from a scratch terminal, or from a pane on another machine. With `appearance.new_window_follow_ssh = true`, a pane that runs ssh gives a new pane that runs the same ssh, as the new-window key does.

A pane opens only when you switch: with a workspace key, a click on the dock, the workspace switcher, the pane navigator or the command palette. These switches do not open a pane:

- `move_and_follow` and other moves that take a pane with them.
- `tuios xpanes`, `tuios select-workspace`, `tuios run-command` and tape scripts.
- The switch back that `return_when_empty` makes.
- The start of TUIOS and an attach to a session.

A workspace gets one pane, also when two clients switch to it at the same time. When you switch away before the pane opens, you stay where you went.

Each client reads the setting from its config file, and a change applies at once. The settings page lists it under Daemon, and `tuios set-config workspaces.new_window_when_empty true` changes it while TUIOS runs.

The daemon must be from the same release or newer. An older daemon opens no pane. Run `tuios kill-server` and start TUIOS again to load the new daemon.

## The dock table

`[dock]` sets what the bar draws: three ordered lists of component names, plus a table for each component that needs one. Edit it in the file, or with the **Dock > Components** editor on the settings page. `set-config` cannot change the lists.

```toml
[dock]
left   = ["mode", "workspaces", "trail", "tape"]
center = ["windows"]
right  = ["transfers", "notifications", "copy-help", "cpu", "ram", "clock", "session-controls"]

[dock.custom.branch]

refresh  = "event:after-focus-change"
on-click = "tuios new-window log -- git log --oneline -20"
```

These lists are the default. A missing list uses the default. An empty list (`left = []`) draws nothing on that side.

The built-in components are `mode`, `workspaces`, `trail`, `tape`, `windows`, `transfers`, `notifications`, `copy-help`, `cpu`, `ram`, `clock`, `session-controls` and `session`. Listing one lets it draw. It still needs its own condition, so `cpu` still needs `show_cpu`. `copy-help` shows the keys of copy mode, multi copy mode and hints mode while the mode is open. See [Mode keys in the dock](/docs/keybindings#mode-keys-in-the-dock).

`transfers` <Since feature="copies-panel" /> shows the copies between machines. It shows nothing while no copy exists. One copy is a bar and a percent, `[####--] 61%`. More copies are a count and a percent, `3 copies 42%`. `waiting` means a link is down. `1 failed` stays until you open the Copies panel. A click opens the [Copies panel](/docs/keybindings#copies-between-machines).

`[dock.clock]` takes `format`, a Go time layout. A layout without seconds refreshes once a minute.

<Since config="dock.session" /> `session` shows the session name, the workspace and the pane, such as `main 2:1`. It is in no default list. `[dock.session]` takes `format`, with `{session}`, `{workspace}` and `{pane}`. It also takes the cell style keys `fg`, `bg`, `bold`, `cap_left` and `cap_right`. `[dock.custom.NAME]` takes the same style keys. Colours are `#rrggbb`.

<Since feature="dock-center-steady" /> When the `center` list has a clock or a custom cell, the centre is at the middle of the terminal. A notification does not move it, and it does not shorten the minimized pane labels. On a crowded bar, the centre moves left to keep the cells on the right on the screen. Click a cut notification to read the full message.

### Custom components

`[dock.custom.NAME]` defines a cell. Put `custom/NAME` in a list to place it.

| Key | Default | What it does |
|-----|---------|--------------|
| `command` | required | Run with `sh -c`. The first line of output is the cell text |
| `refresh` | `"once"` | `once`, a duration such as `"30s"`, `push`, or `event:TYPE[,TYPE]` |
| `on-click` | `""` | Run with `sh -c` when the cell is clicked |
| `max-width` | `24` | Widest the cell may be, in cells |
| `fg`, `bg`, `bold` <Since config="dock.session" /> | unset | The text colour, the ground colour and bold text of the cell. Colours are `#rrggbb` |
| `cap_left`, `cap_right` | unset | Text drawn before and after the cell, in the colour of its ground |

With `push`, the command keeps running and each line it prints replaces the cell. With `event:`, the command runs again when the daemon reports one of those [hook events](/docs/hooks).

A component whose command fails is hidden. `tuios list-dock-components` shows what each component last did and why a cell is missing. `tuios refresh-dock [name]` runs a component again now.

## The hosts table

`[hosts]` names the other machines this daemon links to. Each host is a table.

```toml
[hosts.build]
addr = "gaurav@buildbox"

[hosts.work]
addr = "workstation"
connect_timeout = 5
```

| Key | Default | What it does |
|-----|---------|--------------|
| `addr` <Since config="hosts.*.addr" /> | required | Anything ssh accepts, including an `ssh_config` alias. A host with no `addr`, or with one that starts with `-`, is ignored and logged |
| `connect_timeout` <Since config="hosts.*.connect_timeout" /> | `10` | Seconds one dial may take before the host counts as unreachable |
| `command` <Since config="hosts.*.command" /> | `""` | The `tuios` binary on the host. Empty means the link finds it on the `PATH`, at the usual install paths, or through a login shell |
| `ssh_options` <Since config="hosts.*.ssh_options" /> | `[]` | Extra ssh arguments, placed before the address. Only safe options are accepted. See [Rules for ssh_options](#rules-for-ssh_options). `-A` forwards your ssh agent to the host. See [SSH Agent](/docs/ssh-agent#remote-hosts) |
| `repos_root` <Since config="hosts.*.repos_root" /> | `""` | Where the host keeps its checkouts, as the host reads it, such as `~/src`. `fan --host`, `worktree new --host` and `start-agent` look for a repository there by its origin URL |

You can also manage the table from the shell. These commands edit the file:

```bash
tuios hosts add build gaurav@buildbox
tuios hosts test build
tuios hosts remove build
```

A change that gives a machine less applies at once, also on links that are open. A new host, a host that dials another way, or a change that gives a machine more waits for `tuios config apply` from a terminal outside TUIOS. A daemon restart also applies it. So `tuios hosts add` from a pane waits. A host that you add with "Add a host" on the settings page applies at once. See [Changes that wait](/docs/agents#changes-that-wait).

### Rules for ssh_options

`ssh_options` accepts only options that cannot run code or write files on this machine. Write each option as `-o Keyword=value`, with one plain value and no quotes.

- Accepted examples: `-p`, `-i`, `-l`, `-J`, `Port`, `User`, `HostName`, `HostKeyAlias`, `IdentityFile`, `StrictHostKeyChecking`, the `ServerAlive` options and the algorithm lists.
- Refused: `ProxyCommand`, `LocalCommand`, the known hosts files, `ControlPath`, `-F` and socket forwards.
- Refused: port forwards (`-L`, `-R`, `-D`).
- `-J` and `ProxyJump` take host names only. `ForwardAgent` takes only `yes` or `no`.
- A host `addr` or `command` cannot start with a dash.

TUIOS drops a host with a refused option. `tuios hosts` and the Inbox name the reason. Put a refused option in `~/.ssh/config`, and name that host in `addr`.

```toml
[hosts.build]
addr = "gaurav@buildbox"
ssh_options = ["-J", "bastion", "-o", "ServerAliveInterval=30"]
```

<Callout type="warn" title="Upgrading from v0.8.0">
After the upgrade, look in the Inbox or run `tuios hosts`. A host with a refused option is dropped. Move the option, such as `ProxyCommand` or `LocalForward`, into `~/.ssh/config`. Keep port forwards in `~/.ssh/config` too.
</Callout>

The daemon runs ssh with `BatchMode` on, so a link never asks for a password or about a host key. Run ssh to the host once by hand to accept its key.

### What another machine may do here

The same `[hosts.NAME]` table, read on the machine a link arrives at, also says what the machine of that name may do there. `[hosts."*"]` covers every machine with no table of its own.

```toml
[hosts.laptop]
addr = "laptop"                  # optional: without it nothing is dialled
allow = ["list", "mail", "open", "write", "respond"]
hold_mail = true
hosted_grace = "10m"

[hosts."*"]
allow = ["list", "mail"]
```

| Capability | What it lets the other machine do here |
|------------|----------------------------------------|
| `list` | Read sessions, windows, captures, agent state, the Inbox, prompts, waits and events |
| `mail` | Send and read agent mail, and use the stash |
| `open` | Start sessions, windows, worktrees, fans and agents |
| `write` | Type into panes, close and move windows, set options and names, report agent state, attach, and pull a worktree's work |
| `respond` | Answer for you: prompts, held approvals, `ask-human` questions, dismissing Inbox items and passing on held mail. Also type, from a pane on the other machine, into a pane here that waits on a prompt. The person at the other machine, outside every pane, needs only `write` for that |
| `files` <Since feature="files-capability" /> | Read and write files here, and copy files in and out. Writes land only in the folders of `files_roots`. See [Files over a link](#files-over-a-link) |

`list` also lets the other machine stream the bytes of a pane (`stream-pane`). <Since verb="stream-pane" />

With no table, a machine may `list`, `mail`, `open`, `write` and `files`. `respond` is opt-in. An `allow` that is set replaces that list, and `allow = []` allows nothing. A table that sets `allow` without `files` keeps that machine from your files. Anything not allowed is refused with `forbidden`.

To relay on to this machine's own hosts, a machine needs `list`, `mail`, `open`, `write` and `respond`. A table written for an older tuios that allows those five still relays.

`hold_mail = true` holds mail from that machine to an agent here in your Inbox, marked `held for NAME`, until you pass it on with <kbd>p</kbd>. `hosted_grace` is how long a pane this machine runs for the other one (a window opened there with `--host`) keeps running after the link drops: a duration, `"0"` to end it with the link, 10 minutes when unset, at most 24 hours.

The name is the one the other machine gives for itself, its host name up to the first dot, unless the ssh key it logs in with pins one with `command="tuios stdio-proxy --as laptop",restrict`. Only a pinned name is a boundary. A change that allows less applies to the next call on every link. A change that allows more waits for `tuios config apply`.

### Files over a link <Since config="hosts.*.files_roots" /> [#files-over-a-link]

A machine with `files` can read your files and write new ones. Three keys in its `[hosts.NAME]` table set the limits:

```toml
[hosts.laptop]
allow = ["list", "files"]
files_roots = ["~/Downloads/tuios", "~/dev"]   # where it may write
files_read_roots = ["~/share"]                 # where it may read
files_min_free = "5GiB"                        # the space a write must leave free
```

| Key | Default | What it does |
|-----|---------|--------------|
| `files_roots` <Since config="hosts.*.files_roots" /> | one receive folder | The folders the machine may write in. The default is `~/Downloads/tuios` on macOS and Windows, and `$XDG_DOWNLOAD_DIR/tuios` (or `~/Downloads/tuios`) on other systems. tuios makes it on first use |
| `files_read_roots` <Since config="hosts.*.files_read_roots" /> | not set | The folders the machine may read. Not set means every file you can read, apart from the read deny list. When set, the machine also reads the folders of `files_roots` |
| `files_min_free` <Since config="hosts.*.files_min_free" /> | `"1GiB"` | The free space a write must leave on its disk. A whole number with `B`, `KB`, `MB`, `GB`, `TB`, `KiB`, `MiB`, `GiB` or `TiB`. `"0"` turns the check off |

A path is absolute or starts with `~`. Some places are always closed, whatever the roots say:

- **Writes** never go into `~/.ssh`, `~/.gnupg`, cloud and git credentials, shell start files such as `.bashrc` and `.zshrc`, login items, crontabs, `/proc`, or tuios's own config and state.
- **Reads** never return keys, credentials, keyrings, shell histories, browser profiles, `/proc`, or tuios's own state. A public `*.pub` key in `~/.ssh` is the one exception.
- A file with more than one name (a hard link) is never read over a link. Copy it to a new file to share it.

A refused write says where writes may land and which key to change. A deny list can never name every secret on a machine, so `files_read_roots` is the stronger choice.

Other limits:

- One machine may have at most 8 write streams and 64 unfinished copies here at once. Past that, a write is `busy`, and a copy waits and tries again.
- Files dropped on a pane go to a private drop folder. It holds at most 256 MiB for all drops, for 24 hours.
- A copy another machine starts here keeps to the same rules, also after tuios restarts. When `files` is taken away, its copies here stop.
- A change that widens `files_roots` or `files_read_roots`, removes `files_read_roots`, or lowers `files_min_free` waits for `tuios config apply`. A change that narrows applies at once.

<Callout type="warn" title="Give files only to machines you trust">
A machine with `files` can write any file inside its roots and read any file outside the deny list. A file copy can run code: a binary in a folder on your `PATH`, or a config file that a program reads. Give `files`, and a wide `files_roots`, only to a machine you trust as you trust your own.
</Callout>

See [Remote Hosts](/docs/remote-hosts#copy-files-between-machines) for the copies themselves.

See [`tuios hosts`](/docs/cli-reference#hosts).

### Reaching a host you cannot ssh to directly

A host behind NAT, with no port forward and no jump host, is a network problem to solve under TUIOS. Any tool that pipes stdio to a remote port works as an ssh `ProxyCommand`. `ssh_options` refuses `ProxyCommand`, so name it in `~/.ssh/config`.

Tailscale's [tailcat](https://github.com/tailscale/tailcat) is one such tool. It carries a connection over WireGuard with no Tailscale account and no open port. Run it on the far side against sshd:

```sh
tailcat --serve=22
```

Then add a host to `~/.ssh/config` that uses it:

```text
Host laptop-tailcat
    HostName laptop
    User gaurav
    ProxyCommand tailcat <token> 22
```

Name that host in the host entry:

```toml
[hosts.laptop]
addr = "laptop-tailcat"
```

ssh still decides who may connect: the tunnel only carries bytes to sshd, which asks for your key as usual. A leaked tailcat token gives reachability, not access. TUIOS adds no identity system of its own and opens no listening port.

## The tailscale table

`[tailscale]` changes which tailnet machines `tuios hosts add` and `tuios hosts tailnet` offer as addresses. It never adds a host by itself.

| Key | Default | What it does |
|-----|---------|--------------|
| `enabled` <Since config="tailscale.enabled" /> | `true` | Offer tailnet machines. Empty on a machine that is not on a tailnet |
| `addr` <Since config="tailscale.addr" /> | `"dns"` | Address form: `dns` (MagicDNS name), `name` (short name) or `ip` |
| `user` <Since config="tailscale.user" /> | `""` | ssh login to put before every address |
| `users` | none | Per-machine logins, keyed by short name. Wins over `user` |
| `os` <Since config="tailscale.os" /> | platforms that run TUIOS | Operating systems to offer. An empty list offers every machine |
| `offline` <Since config="tailscale.offline" /> | `false` | Also offer machines that are offline |
| `self` <Since config="tailscale.self" /> | `false` | Also offer this machine |
| `shared` <Since config="tailscale.shared" /> | `false` | Also offer machines shared into your tailnet |
| `include`, `exclude` | `[]` | Glob patterns on the short name and the MagicDNS name. `exclude` wins |
| `max` <Since config="tailscale.max" /> | built in | Most machines to offer |
| `socket` <Since config="tailscale.socket" /> | `""` | Path to the tailscaled socket, if it is not in the usual place |

```toml
[tailscale]
user = "ubuntu"
exclude = ["*-pad-*"]

[tailscale.users]
build = "admin"
```

## The agents table

`[agents]` sets how TUIOS treats the coding agents in its panes. Except for `enabled`, it is outside `list-options`, and `set-config` cannot change it, so a program in a pane cannot loosen it. The daemon reads it at start and again whenever the file changes. See [Inbox and Review](/docs/agent-inbox) for what each part does.

### Turn off agent features

```toml
[agents]
enabled = false
```

`enabled` (default `true`) is the one switch for every agent feature. With it off, TUIOS is only a multiplexer: no agent detection, no agents section on the rail, no Inbox, mail, approvals or agent alerts, and agent commands stop with a message. The change applies at once. It is the first row of the settings page, "Agent features", and `tuios set-config agents.enabled false` from a shell outside TUIOS also sets it. A process in a pane cannot change it. See [Turn Off Agent Features](/docs/agents-off).

### The other agent tables

```toml
[agents.approvals]
enabled = ["claude-code", "opencode"]   # harnesses whose permission prompts the Inbox may answer
hold_seconds = 120                      # 10 to 300
hold_plans = true                       # a plan follows enabled

[agents.approvals.risk]
builtin = true                          # keep the shipped risk rules
panes_may_allow = false                 # a pane with the respond grant may not allow a risky call

[[agents.approvals.risk.rule]]
name = "kubectl apply"
tools = ["Bash"]                        # empty: every tool
pattern = '\bkubectl\s+(apply|delete)\b'   # RE2, matched per command

[agents.permissions]
mode = "strict"                         # open (default) or strict
grants = ["read", "write", "fan"]       # what a pane holds under strict

[agents.recap]
mode = "toast"                          # toast, inbox or off
away = "10m"
test_patterns = ["go test", "pytest"]

[agents.queue]
max = 8                                 # at most 64

[agents.checkpoints]
enabled = true
keep = 50                               # at most 1000
max_untracked_mb = 50                   # a negative value means no limit
```

| Key | Default | What it does |
|-----|---------|--------------|
| `approvals.enabled` <Since config="agents.approvals.enabled" /> | `[]` | Harnesses whose permission prompts wait for an answer from the Inbox: `claude-code` (or `claude`), `opencode` and `kilo`. Empty turns it off |
| `approvals.hold_seconds` <Since config="agents.approvals.hold_seconds" /> | `120` | How long a prompt waits for your answer before the harness asks in its own pane |
| `approvals.hold_plans` <Since config="agents.approvals.hold_plans" /> | `true` | Also hold a plan an agent asks you to approve when it leaves plan mode |
| `approvals.risk.builtin` <Since config="agents.approvals.risk.builtin" /> | `true` | Keep the shipped [risk rules](/docs/agent-inbox#risk-rules) |
| `approvals.risk.panes_may_allow` <Since config="agents.approvals.risk.panes_may_allow" /> | `false` | Let a pane holding the `respond` grant allow a risky call |
| `approvals.risk.rule` <Since config="agents.approvals.risk.rule" /> | none | Your own rules: a `name`, the `tools` it applies to, and an RE2 `pattern` |
| `permissions.mode` <Since config="agents.permissions.mode" /> | `"open"` | `open` gives a pane started with no grants of its own `admin`. `strict` gives it `grants`. Any other value reads as `strict` |
| `permissions.grants` <Since config="agents.permissions.grants" /> | `["read", "write", "fan"]` | What such a pane holds under `strict`. An empty list gives nothing. Add `files` to let a pane copy files near its work. See [Copying files with the files grant](/docs/agents#copying-files-with-the-files-grant) |
| `recap.mode` <Since config="agents.recap.mode" /> | `"toast"` | Where the away recap shows: `toast` in the dock and the Inbox, `inbox` only in the Inbox, `off` only in `tuios agent-log --recap` |
| `recap.away` <Since config="agents.recap.away" /> | `"10m"` | How long you must have been away from a pane for the dock to show its recap |
| `recap.test_patterns` <Since config="agents.recap.test_patterns" /> | built in | Commands that count as a test run in the recap, such as `go test` and `npm test` |
| `queue.max` <Since config="agents.queue.max" /> | `8` | Messages one pane's [queue](/docs/agent-inbox#replying-and-the-queue) holds |
| `checkpoints.enabled` <Since config="agents.checkpoints.enabled" /> | `true` | Save the git work tree of an agent's pane each time the agent finishes a turn that changed a file. See [Checkpoints](/docs/checkpoints) |
| `checkpoints.keep` <Since config="agents.checkpoints.keep" /> | `50` | How many checkpoints one pane keeps, at most 1000 |
| `checkpoints.max_untracked_mb` <Since config="agents.checkpoints.max_untracked_mb" /> | `50` | Leave an untracked file larger than this many megabytes out of a checkpoint. `tuios checkpoint list` names the files left out, and a restore does not change them |

After turning on `approvals.enabled`, run `tuios integration install` for that harness again, so its hook is the version that waits. The grants are `read`, `write`, `fan`, `respond`, `files` and `admin`. See [What a pane may do](/docs/agents#what-a-pane-may-do).

A change to `[agents.permissions]` that gives panes less applies at once. A change that gives more, such as `strict` to `open`, waits. Run `tuios config apply` from a terminal outside TUIOS, or restart the daemon. See [Changes that wait](/docs/agents#changes-that-wait).

## The notify table

`[notify]` sends a push notification when the Inbox gets an item that waits for you. The daemon sends it, so it works when no client is attached. The providers are ntfy, Pushover and a webhook.

```toml
[notify]
web_url = "https://term.example.com/"   # tuios-web, for a link to the item

[notify.ntfy]
url = "https://ntfy.sh/a-long-random-topic"
token_file = "~/.config/tuios/ntfy-token"   # optional
```

| Key | Default | What it does |
|-----|---------|--------------|
| `enabled` <Since config="notify.enabled" /> | `true` | `false` turns every notification off. Nothing is sent without a provider |
| `web_url` <Since config="notify.web_url" /> | `""` | The address of `tuios-web`. Each notification links to `web_url/inbox?item=ID` |
| `content` <Since config="notify.content" /> | `"summary"` | `summary` sends the kind, the pane name and the line the Inbox shows. `title` sends only the kind and the session |
| `quiet_active_seconds` <Since config="notify.quiet_active_seconds" /> | `120` | Hold a notification while you typed at an attached client in this many seconds. `0` sends at once |
| `cooldown_seconds` <Since config="notify.cooldown_seconds" /> | `60` | The shortest time between two notifications for the same pane and kind |
| `max_per_hour` <Since config="notify.max_per_hour" /> | `30` | The most notifications in one hour. `0` sets no limit |
| `allow_http_redirects` <Since config="notify.allow_http_redirects" /> | `false` | Let a provider redirect to a plain `http` address |

`[notify.triggers]` selects the Inbox kinds: `approval`, `plan`, `question` and `ask` are on by default, `mail`, `errored` and `finished` are off. Like `[hosts]`, `[notify]` is not in `list-options`, and `tuios set-config` cannot change it. A new address or a new source for a secret waits for `tuios config apply` from a terminal outside TUIOS. `tuios notify test` sends a test notification through each provider. See [Push Notifications](/docs/push-notifications) for the providers and the secrets.

### Web Push <Since config="notify.webpush" /> [#web-push]

`[notify.webpush]` configures the pushes the daemon sends to a phone that registered for Web Push. It needs no provider.

```toml
[notify.webpush]
subject = "https://example.com/tuios-contact"   # optional
allow_insecure = false
```

| Key | Default | What it does |
|-----|---------|--------------|
| `subject` <Since config="notify.webpush.subject" /> | `https://tuios.dev/push` | The VAPID subject: an `https` URL or a `mailto:` address that a push service can use to contact you |
| `allow_insecure` <Since config="notify.webpush.allow_insecure" /> | `false` | Let tuios send to a push service on a loopback or private address, by `https` or `http`. A change to `true` waits for `tuios config apply` |

See [Push Notifications](/docs/push-notifications#web-push-to-a-phone).

## Hooks

`[hooks]` runs shell commands on window, workspace, session and agent events. Event names use hyphens, such as `after-new-window`. See [Hooks](/docs/hooks) and `tuios list-hooks`.

## Validation

The file is checked when it loads. Problems are errors or warnings.

**Errors** are keys TUIOS cannot read, such as `"ctrl+nope"` or `"ctrl+"`. TUIOS ignores each of these keys and loads the rest of the file. See [When a key is wrong](#when-a-key-is-wrong).

**Warnings** keep the key. They cover unknown values (which fall back to the default), unknown title placeholders, actions with no key, two actions on one key in the same section, and the macOS `alt+` advice.

TUIOS shows the number of problems when it starts, for example `2 config problems, see the log viewer`. The log viewer (leader <kbd>D</kbd> <kbd>l</kbd>) shows each problem.

<Callout type="warn" title="A file that does not parse">
If `config.toml` is not valid TOML, TUIOS cannot read any of it. At startup, TUIOS uses the built-in defaults and shows a config problem. If you save such a file while TUIOS runs, TUIOS keeps the config that it has.
</Callout>

## When a key is wrong

TUIOS ignores a key that it cannot read, such as `ctrl+nope`. It loads the rest of the file. Your other keys, the leader and the other settings stay as you wrote them.

The action of an ignored key gets a key as follows:

- If the action has another key that TUIOS can read, the action keeps that key.
- If the action has no other key, it gets its default key.
- If another action already has that default key, the action has no key.
- If TUIOS cannot read `leader_key`, the leader is `ctrl+b` until you correct it.

TUIOS does not change your file. Correct the key, then save. The change applies at once.

To find the ignored keys:

- Look for the `config problems` notification when TUIOS starts.
- Open the log viewer (leader <kbd>D</kbd> <kbd>l</kbd>). Each line names the key and its file.
- Run `tuios keybinds doctor`. It lists each key by file and says what TUIOS does instead. See [Keybindings](/docs/keybindings#keys-tuios-cannot-read).
- Run `tuios config apply`. It lists the keys it ignored.

The same rule applies to keys in an included file and in `config.d`.

## One config on macOS and Linux

You can use one `config.toml` on a Mac and on a Linux machine, for example from a dotfiles repo. TUIOS reads `opt+` and `option+` as `alt+` on every platform. On Linux, `opt+1` is `alt+1`.

```toml
[keybindings.workspaces]
switch_workspace_1 = ["opt+1"]   # Option+1 on macOS, Alt+1 on Linux
```

`tuios keybinds doctor` lists these keys under `OPT KEYS READ AS ALT`. This is for information. You do not need to change them.

## Troubleshooting

**My config seems ignored.**

1. Run `tuios config path` to confirm which file TUIOS reads. Run `tuios config files` to see every file that TUIOS reads.
2. Look for the `config problems` notification when TUIOS starts. Open the log viewer (leader <kbd>D</kbd> <kbd>l</kbd>) to see each problem.
3. Run `tuios keybinds doctor`. It lists each key that TUIOS cannot read, and the leader that TUIOS uses. TUIOS ignores only those keys. See [When a key is wrong](#when-a-key-is-wrong).
4. If the log says the file does not parse, correct the TOML. TUIOS uses the defaults until then.
5. On Linux, a key copied from a Mac works. `opt+` is `alt+` on every platform.

**A setting changed nothing.**

1. Check the [table of what applies live](#applying-changes). A saved keybinding works at the next key press.
2. Check that the file parsed. Look for an error notification, or run `tuios keybinds list`.
3. Check whether a command-line flag is overriding it.
4. Check whether a later file sets the key. Run `tuios config origin <key>`. An old `config.toml` that sets every key hides the other files. Run `tuios config prune` to remove its default values. See [Split the Config](/docs/config-files#clean-up-an-old-configtoml).
5. For a hook, check the event name spelling with `tuios list-hooks`.

**A key does nothing.** Run `tuios keybinds explain <key>` to see every place it is bound, and `tuios keybinds doctor` for conflicts.

## Examples

### Browser-style keys

```toml
[keybindings.window_management]
new_window = ["ctrl+t"]
close_window = ["ctrl+w"]
next_window = ["ctrl+tab"]
prev_window = ["ctrl+shift+tab"]
```

### Screen-style leader

```toml
[keybindings]
leader_key = "ctrl+a"

[keybindings.prefix_mode]
prefix_new_window = ["c"]
prefix_split_horizontal = ["S"]
prefix_split_vertical = ["V"]
prefix_session_switcher = ["s"]
prefix_scrollback = ["/"]
```

In this example, `S` and `s` are taken by the splits and the switcher, so the scrollback browser moves to `/`. Keys inside one section must not collide.

```toml
[appearance]
theme = "nord"
border_style = "hidden"
dockbar_position = "hidden"
shared_borders = true
whichkey_enabled = false
window_title_format = "{index}: {title}"
scrollback_lines = 50000
max_fps = 120
```
